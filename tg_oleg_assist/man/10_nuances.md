# Нюансы, edge-cases и потенциальные проблемы

## Ключевые архитектурные решения

### Синхронный Anthropic SDK в async-коде

`app/services/ai_client.py` использует `anthropic.Anthropic` (синхронный клиент), а не `anthropic.AsyncAnthropic`. Вызов `self.client.messages.create(...)` — блокирующий. Это означает, что во время ожидания ответа от Claude event loop asyncio будет заблокирован. При большом числе одновременных запросов это может стать узким местом.

### Кэш ChatContext живёт только в рамках одного запроса

`ChatContextResolver` создаётся заново в каждом вызове `_process_message()`. Его `self._cache` — это словарь на время жизни одного объекта. Практический эффект: нет риска устаревшего кэша между запросами, но при обработке одного сообщения, если несколько сервисов обращаются к одному чату через один объект `resolver` — данные кэшируются. Если же `resolver` создаётся повторно внутри одного запроса — делается лишний SQL-запрос.

### Пользователи не создаются автоматически

В compliance-режиме бот ищет пользователя в таблице `users` по `tg_id`. Если запись не найдена — сообщение тихо игнорируется. Это сознательное решение (только заведённые администратором люди мониторятся), но может вызвать путаницу при настройке нового чата.

### Личный счёт не сбрасывается при блокировке

Уведомление пользователю содержит фразу "после разблокировки баллы будут сброшены", но в коде никакой логики сброса нет. Баллы "истекают" естественно через скользящее окно 30 минут. Технически корректно, но формулировка вводит в заблуждение.

## Защита от двойного срабатывания

### IdempotencyGuard (webhook)

Не защищает от перезапуска процесса. Если бот упал и перезапустился за 10 минут — дублирующийся `update_id` из кэша Telegram может быть обработан повторно.

### In-memory множества TimerWorker

`_planner_checks_done`, `_report_checks_done`, `_growth_checks_done` сбрасываются при перезапуске. После рестарта бота в "нужное" время задание выполнится снова:
- Plan-fact защищён на уровне БД (`fact_checked_at IS NULL`).
- Планёр пришлёт повторное утреннее сообщение или запрос обратной связи.
- Напоминания об отчётах отправятся повторно.

### resolve_all_with_feature — загружает ВСЕ активные чаты

`ChatContextResolver.resolve_all_with_feature(feature)` — запрашивает все активные чаты из БД без фильтрации на уровне SQL, затем проверяет feature-флаг в Python. При большом числе чатов (тысячи) это станет проблемой.

## Внешние зависимости

### Anthropic Claude API

- Все ключевые функции (анализ этики, парсинг планов, планёр, ROP-отчёты, Bitrix-парсинг) зависят от Claude.
- Для этики есть fallback (keyword-matching), для остального — нет.
- При prolonged outage: планирование не будет работать, РОП-отчёты не будут переформатироваться, планёр не сможет выдать анализ.

### Внешняя БД 2_kadry_4

Все функции, связанные с данными о выходах сотрудников, зависят от этой БД:
- `exits_wa` — данные для план-факта и метрики планёра
- `exits_wa_stajers` — данные для РОП-отчётов
- `ref_projects_wa`, `ref_project_groups` — справочники

При недоступности 2_kadry_4:
- Планирование недоступно (не загружается справочник)
- Plan-fact не может посчитать факт (entries помечаются `no_data`)
- РОП-отчёт форматируется с "нет данных" в полях из этой БД

Бот подключается к обеим БД через **один и тот же connection pool** (одна строка подключения в `DATABASE_URL`). Обе БД должны быть на одном сервере или доступны через один хост.

### Telegram Bot API

- Блокировка пользователей требует прав администратора с разрешением "Restrict members"
- Удаление сообщений (РОП-реформат) требует прав "Delete messages"
- Если бот потерял права — операции тихо завершатся с ошибкой в логах

## Потенциальные проблемы

### Состояние гонки при параллельных сообщениях

Если два сообщения от разных пользователей одного чата обрабатываются одновременно, оба могут прочитать `dialog_states` до того, как один из них запишет изменение. Транзакционность SQLAlchemy async защищает от частичных записей, но последовательность финальных состояний может зависеть от порядка коммитов.

### Emoji в сообщениях пользователям

Правила кодстайла проекта запрещают emoji в коде, но они активно используются в строках уведомлений (`notification.py`, `timer_worker.py`, `bitrix_service.py`, `report_service.py`). Это не баг, но противоречие между стандартом и реализацией.

### Отсутствие retry для Claude API

`AIClient` не делает повторных попыток при временных ошибках сети или rate limit. При единичном сбое вся операция падает. Для критичных функций (планирование, реформат РОП) это означает потерю данных — пользователю придётся отправить сообщение ещё раз.

### Нет мониторинга лагов TimerWorker

Если одна из `_check_*` функций зависает, вся итерация воркера блокируется. Следующая итерация начнётся только через 30 секунд после завершения предыдущей. Таймаута на отдельные проверки нет.

### Накопление scoring_events

Таблица `scoring_events` пишется при каждом нарушении и не имеет встроенного механизма архивирования. При активном использовании может вырасти значительно. Запросы по ней (скользящее окно) используют индекс по `created_at`, но периодическая очистка старых данных не реализована.

## Что нужно сделать при настройке нового чата

1. Добавить бота в группу (автоматически создастся запись в `chats` с `mode='viewer'`)
2. В БД обновить `mode` нужного чата
3. Выставить `features` и `config` JSON
4. Завести пользователей в таблице `users` с нужными ролями и `tg_id`
5. Если нужен трекинг отчётов — завести `report_types` и `report_responsible`
6. Для планёра ГД — задать `planner_ceo_user_id` в `chats.config`
7. Для plan-fact отчётов — задать `GROWTH_REPORT_CHAT_ID` в `.env`
