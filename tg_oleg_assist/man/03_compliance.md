# Compliance-конвейер: этика, оценка, уведомления

Запускается для сообщений из чатов с `mode='compliance'`. Каждый из трёх сервисов (этика, упоминания, отчёты) включается независимо через feature-флаги. Ошибка в одном сервисе не прерывает работу остальных — каждый обёрнут в отдельный `try/except`.

```python
if ctx.has_feature('ethics_analysis'):   await _process_ethics(...)
if ctx.has_feature('mention_tracking'):  await mention_service.process_message(...)
if ctx.has_feature('report_reminders'):  await report_service.process_message(...)
```

## Анализ этики

### EthicsAnalyzer

`app/services/ethics_analyzer.py` — два пути анализа: AI (основной) и keyword-matching (fallback).

**AI-путь:**

Отправляет в Claude запрос с системным промптом `SIGNAL_DETECTOR_PROMPT` (`app/prompts/signal_detector.py`). Промпт описывает 7 категорий нарушений (S1–S7) с примерами фраз, правилами анализа и требуемым форматом JSON-ответа.

Claude возвращает:
```json
{
  "signals": [
    {
      "rule_id": "S3",
      "category": "aggression",
      "signal_type": "implicit",
      "matched_text": "надоело с этим разбираться",
      "confidence": 0.88
    }
  ],
  "total_weight": 3,
  "risk_assessment": "medium",
  "reasoning": "Сообщение содержит неявную агрессию..."
}
```

Сигналы с `confidence < 0.7` отбрасываются. Вес каждого сигнала берётся не из ответа Claude, а из `rules.yaml` — Claude может ошибиться с весом, справочник авторитетнее.

**Fallback (при недоступности Claude API):**

Простой keyword-matching: для каждого правила проверяется, содержит ли текст (в нижнем регистре) хотя бы одну из `explicit_signals`. Если да — добавляется один сигнал с `confidence=0.9`.

**Правила (rules.yaml):**

| ID | Категория | Вес | Примеры |
|---|---|---|---|
| S1 | blaming | 3 | "это из-за тебя", "ты виноват", "по твоей вине" |
| S2 | devaluation | 1 | "очевидно же", "это ерунда", "элементарно" |
| S3 | aggression | 3 | "мне надоело", "это бесит", "полный бред" |
| S4 | passive_aggression | 2 | "мне всё равно", "без обид, но", "как скажете" |
| S5 | manipulation | 4 | "нормальные люди так не делают", "все так думают" |
| S6 | categorical | 4 | "точка", "вопрос закрыт", "это не обсуждается" |
| S7 | behavior | 2 | сарказм, ирония, высмеивание (только implicit/non_textual) |

**Уровни риска:**

- `low` — суммарный вес 1–2
- `medium` — 3–5
- `high` — 6+

### ScoringEngine (FSM диалога)

`app/services/scoring_engine.py` — накапливает баллы нарушений по чату в скользящем временном окне и управляет состоянием диалога.

**Состояния диалога:**

```
NORMAL (0-2) --> TENSION (3-5) --> CONFLICT (6-9) --> ESCALATION (10+)
```

Для каждого чата в таблице `dialog_states` хранится текущее состояние. История переходов — в `state_transitions`.

**Как обновляется состояние:**

1. Сигналы от `EthicsAnalyzer` сохраняются в `scoring_events` (с весами, категориями, confidence).
2. Считается сумма весов всех событий за последние 30 минут: `SUM(weight) WHERE created_at >= now - 30min`.
3. Сначала проверяются условия из `conflict_rules.yaml` (C1–C6). Если хотя бы одно выполнено — сразу применяется указанное в нём состояние.
4. Если ни одно условие не сработало — состояние определяется по числовым диапазонам.

**Условия из conflict_rules.yaml:**

| ID | Тип | Условие | Результат |
|---|---|---|---|
| C1 | score_threshold | 6+ баллов за 30 мин | CONFLICT |
| C2 | repetition | passive_aggression 2+ раза за 15 мин | CONFLICT |
| C3 | mutual_escalation | aggression+blaming от 2+ разных пользователей за 20 мин | CONFLICT |
| C4 | score_threshold | 3+ балла за 5 мин | TENSION |
| C5 | score_threshold | 10+ баллов за 30 мин | ESCALATION |
| C6 | repetition | manipulation 2+ раза за 20 мин | ESCALATION |

**Личный счёт пользователя** (`calc_user_score`): аналогичный запрос, но с фильтром по `user_id`. Используется для пороговых предупреждений конкретному сотруднику.

### ArbitrationService

`app/services/arbitration.py` — определяет, кому отправить алерт о нарушении.

Матрица арбитража (по роли автора и уровню риска):

| Риск | Manager | Deputy Director | Director |
|---|---|---|---|
| low | сам (self-feedback) | сам | сам |
| medium | куратор (deputy director) | директор | HR |
| high | HR | HR | HR + нейтральный замдиректора |

"Нейтральный замдиректора" — это замдиректора из **другого** оргподразделения, чтобы обеспечить независимость.

Если куратор менеджера не назначен — fallback на HR. Если HR-пользователей нет в БД — `arbiter_ids=[]` (ситуация требует ручного вмешательства).

### Логика уведомлений (NotificationService)

После ArbitrationService в `_handle_notifications()` принимается решение о типе уведомлений. Важно: пороги проверяются как "пересечение снизу вверх" — уведомление отправляется только при первом превышении порога, не при каждом сообщении.

```
user_score_after >= 10 AND user_score_before < 10
    --> send_block_notification()     (личка: "вы заблокированы на 60 мин")
    --> restrict_chat_member()        (реальная блокировка через Telegram API)
    --> send_to_chat()                ("Пользователь X ограничен на 1 час")

user_score_after >= 8 AND user_score_before < 8
    --> send_ethics_final_warning()   (личка: "последнее предупреждение")

user_score_after >= 6 AND user_score_before < 6
    --> send_ethics_soft_warning()    (личка: "вы приближаетесь к блокировке")

иначе (низкий риск, is_self=True)
    --> send_ethics_self_feedback()   (личка: мягкая обратная связь)
```

Параллельно (независимо от блокировки):
- Если арбитр внешний (`is_self=False`) — каждому арбитру отправляется `send_ethics_arbiter_alert()` с деталями нарушения.
- Если новое состояние CONFLICT или ESCALATION — всем HR-пользователям отправляется `send_state_notification()`.

## Трекинг упоминаний (MentionService)

`app/services/mention_service.py` — фиксирует, когда один пользователь обращается к другому.

Обнаруживает три типа упоминаний:
- **reply** — ответ на конкретное сообщение пользователя
- **username** — `@username` в тексте
- **text_mention** — Telegram entity типа `text_mention` (для пользователей без username)

При обнаружении создаётся запись в `mentions` с дедлайном (по умолчанию 15 минут из `ctx.config`). Когда упомянутый пользователь сам что-то пишет в чат — все его ожидающие упоминания автоматически закрываются со статусом `ANSWERED`.

Просроченные упоминания (`status=WAITING`, `deadline_at < now`) обрабатывает `TimerWorker` каждые 30 секунд: ставит статус `OVERDUE`, отправляет напоминание в личку и/или в чат (по настройкам).

## Контроль отчётов (ReportService)

`app/services/report_service.py` — фиксирует сдачу регулярных отчётов.

**Детекция:** Проверяет первую строку сообщения на совпадение с ключевыми словами из таблицы `report_types`. Для РОП-отчётов есть дополнительный fallback: если маркер не найден в первой строке, `detect_rop_report()` проверяет всё содержимое на характерные признаки РОП-отчёта.

**Специальная обработка РОП-отчётов:**

Если включён feature-флаг `rop_reformat` и сообщение определено как "Отчёт по лидам" — запускается полный пайплайн переформатирования:
1. Claude парсит сообщение, извлекает структурированные данные (дата, количество лидов, операторы, конверсия)
2. Запрашивается внешняя БД `2_kadry_4.exits_wa_stajers` для получения данных по записям, потребности и выходам
3. Формируется красиво отформатированное сообщение с цветовыми индикаторами
4. Оригинальное сообщение удаляется из чата, новое публикуется

Если включена валидация (`rop_reformat` выключен, но тип РОП), неправильно оформленные отчёты удаляются из чата с объяснением в виде публичного ответа (`@username, отчёт удалён...`).

**Регистрация:** Отчёт считается общегрупповым — если хоть один ответственный сдал, напоминания другим не отправляются.
